# 产品化与优化方向评估

> 本文基于仓库当前状态（单文件 `pose_viewer.html` + Python 离线管线 + 火山引擎分析支线）给出中长期演进判断，不涉及具体实现 PR。与 `pose-viewer-frontend-refactor-plan.md` 互补：那份文档聚焦当前页面结构重构，本文聚焦产品形态、商业落点与技术债清偿。

## 1. 现状判断

### 1.1 技术资产盘点

- **评分内核**：躯干参考系重投影 + 骨骼向量余弦 + 手部 handedness 匹配，已内建降级路径。这是仓库最有壁垒的一块。
- **数据管线**：MediaPipe Tasks（Python 离线）→ JSON → MediaPipe Solutions（浏览器在线）的解耦架构，让"标准动作"成为可交换资产。
- **分析支线**：emoji 时间线 / 颜色 + 音频时间线 / 火山 ARK Responses API，目前是独立脚本形态，尚未反哺评分主线。
- **素材库**：`wudao/` 内 9 段舞蹈示例 + 配套 `_pose.json`，可作为冷启动内容。

### 1.2 结构性弱点

| 维度 | 现状 | 影响 |
| --- | --- | --- |
| 前端形态 | 5600+ 行单文件 `pose_viewer.html`，`App.jsx` 原型闲置 | 新功能边际成本高，协作难度大 |
| 数据层 | 标准动作是仓库内 JSON，用户自传 JSON 也不落盘 | 无"我的进度/历史"，无法做留存 |
| 账户体系 | 无 | 不能做社交、排行榜、订阅 |
| 评分语义 | 纯几何相似度 | 对节奏、表现力、舞感无感知 |
| 分析支线 | 与评分互不通 | emoji/颜色时间线的语义信息没有进入实时 HUD |
| 移动端 | 竖屏布局已做，但非真沉浸全屏、非 PWA、非 App | 最重要的使用场景（举着手机跳）体验最弱 |
| 设备依赖 | 前端摄像头 + 浏览器 MediaPipe Solutions | iOS Safari / 低端 Android 的稳定性与首屏加载是瓶颈 |

## 2. 产品形态选择

以下四个方向互不排斥，但资源/目标用户/商业模型差异很大，应明确主攻一个。

### 2.1 方向 A：面向 C 端的"跟练 App"（推荐主攻）

**定位**：半身 / 手势舞跟练，对标"燃脂镜"「Zepp Linkage」但轻量化、内容化。

**核心场景**：宿舍 / 卧室 / 办公室竖屏手机跟练 30–90 秒短舞。

**MVP 关键能力**：
1. 动作库（先手工收录 50–100 个短动作，`_pose.json` 作为底层资产）。
2. 实时评分 + 逐拍反馈 + 结束页动作回放。
3. 录制自己的跳舞片段 → 自动合成"对比视频"（左导师右用户 + 分数字幕）。
4. 社交分享：导出短视频/GIF，埋"由 XX 生成"水印。

**商业模型**：免费 + 订阅（完整动作库 / 去水印导出 / 高级分析）。

**为什么可行**：仓库已经有评分内核和动作库雏形，缺的是内容运营与 App 壳。

**主要风险**：C 端获客成本、内容版权（舞蹈原曲 & 编舞）、iOS/Android 端 MediaPipe 的设备适配。

---

### 2.2 方向 B：面向 B 端的"动作 SDK / API"

**定位**：把评分内核打包给 K12 舞蹈教育、健身 App、儿童编程/体感课等客户。

**产品形态**：
- Web SDK：把 `pose_viewer.html` 的评分/对齐核心抽成 npm 包。
- REST：上传视频 → 返回姿态 JSON + emoji 时间线 + 关键动作切片。
- 可选的本地推理（WASM / ONNX）包，避免用户视频离开本地。

**商业模型**：按调用量 / License。

**为什么可行**：评分算法相对独立，已有 Python 提取脚本 + 浏览器端推理两套实现，能较快拆分。

**主要风险**：B 端销售节奏慢，需要一个可 demo 的范本客户。

---

### 2.3 方向 C：内容创作工具（"emoji 谱面编辑器"）

**定位**：把 emoji 时间线分析 + 姿态 JSON 结合，做成"给编舞者/运营用"的谱面工具。

**核心场景**：创作者拖入一段视频 → 自动得到节拍、动作段落、emoji 语义标签、颜色变化 → 手工微调 → 导出跟练包（JSON + 封面 + 节拍映射）。

**为什么可行**：仓库已有 `analyze_video_emoji_volcengine.py` / `analyze_emoji_color_timeline_volcengine.py` / `analyze_pose_emoji.py` 三条分析脚本，产品化后可让 A / B 方向的"内容供给"从瓶颈变成护城河。

**主要风险**：用户基数很小，通常作为 A 方向的上游工具而不是独立产品。

---

### 2.4 方向 D：体感互动装置 / 线下

**定位**：商场快闪、展会、KTV、品牌活动的大屏互动。

**为什么可行**：半身评分对空间要求低，一台笔记本 + 摄像头 + 大屏就能跑；`wudao/` 的 emoji 化输出天然适合做视觉效果。

**主要风险**：单点收入非规模化，除非做成可复制的"盒子产品"。

---

### 2.5 推荐路径

**Phase 1（0–3 个月）**：方向 A 的 MVP + 方向 C 作为内部工具。
**Phase 2（3–9 个月）**：A 积累用户与内容，同时把评分内核抽成方向 B 的 SDK，对外 1–2 个合作客户验证。
**Phase 3（9 个月+）**：根据 A/B 哪条现金流跑得通，决定是否扩 D。

## 3. 技术优化方向

按"做完就能直接支撑上述产品方向"的顺序排列。

### 3.1 架构与工程化（产品化前提）

| 项 | 建议 | 价值 |
| --- | --- | --- |
| 前端拆分 | 把 `pose_viewer.html` 迁到 Vite + TS + 轻框架（Svelte/Preact 都行，不一定要 React），按"核心内核 / UI / 资产"分层 | 行数降一半；新功能成本指数级下降 |
| 核心内核独立包 | `packages/pose-core`：`getPoseReference` / `transformPointsWithReferences` / `comparePoses` / `normalizeHandLandmarks` 等纯函数，零 DOM 依赖 | 同时服务方向 A 与方向 B |
| 类型系统 | 给 `frames[]` / `pose_landmarks` / `hands[]` / `extract_config` 写一份共享 Schema（zod / JSON Schema），Python 与 TS 共用 | 避免 Tasks / Solutions 字段对齐时的静默错位 |
| 自动化测试 | 至少给评分内核加黄金样本回归（几段 `_pose.json` + 已知评分），加到 CI | 替换模型或改参数时不再靠肉眼 |
| 仓库瘦身 | `*.mp4` / `*.task` / `test_output.json` 迁到 Git LFS 或独立 CDN；`1.md`、`tmp_audio.wav`、`tmp_frames/`、`emoji_crops/` 等中间产物清出历史 | 当前 clone 成本过高，不利于多人协作 |
| 代码风格 | eslint + prettier + ruff/black + pre-commit | 门槛工程，不展开 |

### 3.2 数据与内容层

- **动作库后端化**：把 `_pose.json` 放到对象存储（TOS/S3），前端按需拉取；加一层索引表（难度、时长、BPM、封面、版权）。
- **版本化**：同一首舞的不同模型/参数提取的 JSON 应带 `extract_version`，前端根据内核版本兼容回退。
- **封面与预览**：每个动作生成 3 秒 mp4 + 首帧图 + emoji 标签，首页才能"像小红书一样选动作"。
- **用户产物**：练习分数、录像片段、对比视频入库（先用 Supabase / PocketBase 等轻后端），为留存打底。

### 3.3 评分算法升级

现有几何相似度是"标尺"，离"像不像在跳舞"还有距离。三条值得投入的深化：

1. **时间对齐**：当前按固定 `playSpeed` 对齐帧，人的动作有延迟与漂移；引入 DTW（动态时间规整）或基于音乐节拍的软对齐，能显著提升用户感知到的"被理解度"。
2. **动作段语义**：把 `analyze_pose_emoji.py` 的 segment 结果反哺到主线——每段给"摆手 / 比心 / 扭胯"这类标签，练习页即时显示"下一拍：✌️比耶"。
3. **表现力特征**：加速度、关节跃度、对称性等时域特征；现在只打"位置像不像"，无法区分"到位但死板"和"到位且有力"。

### 3.4 可选项：端侧推理 & 模型选择

- 浏览器端目前用 MediaPipe Solutions（较老），可评估迁移到 MediaPipe Tasks 的 Web 版本或 ONNX Runtime Web + MoveNet/BlazePose；收益是 Python 端与前端同源，索引对齐问题消失。
- 低端 Android / iOS Safari 做降级检测（检测 FPS < 15 自动降分辨率或切轻量模型）。
- 对方向 B（SDK）来说，WASM 端侧推理是"数据不出端"的卖点。

### 3.5 隐私与合规

- C 端涉及摄像头：首页明确"视频仅本地处理"（这点相对易做，因为推理在浏览器本地），只有用户主动导出对比视频时才上传。
- 分析支线用火山 ARK 时：用户视频上传到 TOS 必须有显式授权文案 + 过期策略 + 可主动删除。
- 儿童场景（方向 B 的一个主要客户群）需要过 COPPA/《个人信息保护法》的儿童条款。

### 3.6 前端体验（承接 `pose-viewer-frontend-refactor-plan.md`）

- 原生 App 壳（Capacitor / Tauri Mobile / 纯 PWA）：解决浏览器全屏不彻底、横屏强制、后台挂起、相机权限引导等问题。
- 低端设备体验分级：`state` 中加 `deviceTier`，据此切换 HUD 详情、分辨率、是否跑手部模型。
- 可访问性：色盲友好的评分色阶、文字化降级路径（目前 HUD 只在文字提示，方向是对的，继续往下压）。

## 4. 路线图建议（12 个月）

### Phase 1：MVP（0–3 个月）

- 前端拆包（`pose-core` + Vite 应用），核心评分函数有 95% 以上覆盖的黄金样本测试。
- 仓库瘦身（大文件移出主仓）。
- 动作库接入对象存储，上架 30 首短舞（含封面与 BPM）。
- PWA 壳 + iOS/Android 首屏性能达标（LCP < 2.5s on 4G）。
- 用户系统 + 练习历史最小闭环。

### Phase 2：留存与扩品（3–9 个月）

- 录制合成"对比视频"并带水印分享，看增长是否由社交分享带起来。
- 算法引入 DTW 对齐 + 表现力特征，评分从"像不像"升级到"像且有劲"。
- `analyze_pose_emoji.py` 升级为谱面编辑器内部工具（方向 C），为方向 A 稳定供给内容。
- 方向 B 的 SDK 抽取出第一版，对外 1–2 家客户 PoC。

### Phase 3：分叉（9–12 个月）

- 看方向 A 的次日/7 日留存 + ARPU，决定是向 C 端深耕还是转向 B 端 SaaS 化。
- 若留存弱但技术被认可，主动转方向 B；若内容 + 社交闭环成立，继续 A 并把 D 作为品牌事件。

## 5. 需要先做出的决策

1. **核心内核是否要离开 `pose_viewer.html`？**（决定能否同时服务 A 和 B）
2. **是否引入用户账户与后端？**（决定能否做留存、排行榜、订阅）
3. **动作版权怎么处理？**（自研原创编舞 / 购买授权 / UGC 创作者分成——三条路完全不同）
4. **评分算法投入的天花板定在哪？**（仅几何相似度 / 加 DTW / 走到动作语义与表现力，决定研发团队是否需要算法同学）
5. **火山引擎分析支线是否并入主线？**（若并入，emoji/音频语义就是方向 A 的差异化；若不并入，是否干脆剥离）

## 6. 当前可以立刻动手的低风险改进

- 核心评分函数加黄金样本测试（1–2 天）。
- `*.mp4` / `*.task` / `test_output.json` 移出主仓 + `.gitattributes` 配 LFS（0.5 天）。
- `App.jsx` 明确删除或标注废弃（避免继续误导）。
- 共享 JSON Schema（`frames[]` / `hands[]` / `extract_config`）在 `docs/` 落盘，Python 与前端各自引用（1 天）。
- 动作库封面与 BPM 元信息补齐，`wudao/` 下加 `index.json`（0.5 天）。

这一组不依赖方向决策，做完即收益。
